# 三端更新与发布

默认将构建发布到 GitHub，标记为 **测试版（Pre-release）**，允许用户下载安装。只有维护者明确要求发布正式版时才能转为稳定版；通过构建或测试不等于获得正式发布授权。

工作台在前台运行时低频检查更新。检查成功后至少隔 24 小时，失败后至少隔 30 分钟。三端查询本仓库最近 20 个 GitHub Release，从中按发布时间找到带有 `update.json` 的最新非草稿版本，支持测试版与正式版；测试版在更新界面明确标注。旧的、没有三端清单的发布仍可手动下载，不影响完整清单的发现。不能读取清单时显示失败，不能误报已是最新版。

用户查看说明后选择下载。下载前重新读取清单，确认包仍与所选版本相同。三端核对大小和 SHA-256；下载与检查不会自动关闭终端。

| 平台 | 安装与重启 |
| --- | --- |
| macOS | 等终端结束后点「安装并重启」。校验包身份、内置版本和代码签名，在原位置替换并保留旧包。安装目录不可写时可手动安装。 |
| Windows | 等终端结束后点「退出并安装」。校验 NSIS 包后交给安装程序继续。 |
| Android | 由系统确认覆盖安装。包名和签名必须相同，且 `versionCode` 更高。开发签名和发行签名分别匹配，不因“测试版”标签混用。 |

覆盖安装保留用户数据目录中的配置、Key 和历史；不要为了更新卸载应用。Termux、Debian、虚拟机和 CLI 按各自的方式升级。

## 自动测试版

推送到 `main` 或手动运行 **Tri-platform build** 会构建、测试三端。CI 在独立 checkout 内按 `github.run_number` 增加各端数字版本，不改写源码中的版本。全部成功后先建草稿，上传三端安装包、`SHA256SUMS.txt`、`update.json`，最后公开为 Pre-release，不占用 GitHub 稳定版 latest。

更新说明默认取 `docs/preview-notes.zh-CN.md`，可手动输入本批说明。版本从真实产物读取，清单由 `scripts/build-update-manifest.py` 生成，包含渠道、架构、版本、地址、大小、哈希；Android 额外记录版本代码和签名类型。

Android 测试包的签名必须固定。Actions secret `WORKBENCH_ANDROID_PREVIEW_KEYSTORE_BASE64` 存放既有开发签名密钥，CI 恢复后通过显式签名路径构建 debug APK，再比较 APK 证书与恢复的密钥证书，避免 runner 默认调试签名导致不能覆盖。密钥不可进入仓库、日志或发布附件。已有其他签名的安装只能使用同签名来源的包。

Windows 单独工作流也只发布可手动下载的测试版；三端应用内更新继续使用完整发布清单。

## 正式版

仅在维护者明确下令后准备。各端版本须高于已经发布的测试包；Android 使用固定发行签名，测试签名用户不能无损跨签名覆盖。生成稳定渠道清单、完成上一版到新版的更新验证后再发布并标为正式版，不自动提升历史测试包。

第一版尚不能发现测试版的旧客户端，需要手动覆盖安装一次带此逻辑的新客户端，之后可在应用内检查更新。
