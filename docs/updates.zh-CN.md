# 三端更新与发布

日常构建发布到 GitHub，通常标记为测试版（Pre-release），允许用户下载安装。客户端成熟度只由版本号决定：`0.x.y` 显示为测试版，`1.0.0` 及更高主版本显示为正式版。GitHub Release 的 Latest / Pre-release 标记不参与客户端更新筛选或成熟度判断；无需为应用内更新把 Release 改成正式版。

工作台在前台运行时低频检查更新。检查成功后至少隔 24 小时，失败后至少隔 30 分钟。默认稳定版读取 `update-feed/stable.json`，用户在更新面板勾选「接收测试版更新」后读取 `preview.json`，两种通道的缓存和检查时间彼此隔离。固定清单不可用或无效时，再查最近 20 个 Release 的清单作为备用。稳定版同时同步旧客户端使用的 `update.json`。客户端成熟度由版本号决定，`0.x.y` 是测试版，`1.x.y` 及更高版本是正式版。

用户查看说明后选择下载。下载前重新读取清单，确认包仍与所选版本相同。三端核对大小和 SHA-256；下载与检查不会自动关闭终端。

| 平台 | 安装与重启 |
| --- | --- |
| macOS | 等终端结束后点「安装并重启」。校验包身份、内置版本和代码签名，在原位置替换并保留旧包。安装目录不可写时可手动安装。 |
| Windows | 等终端结束后点「退出并安装」。校验 NSIS 包后交给安装程序继续。 |
| Android | 由系统确认覆盖安装。包名和签名必须相同，且 `versionCode` 更高。首个正式版沿用公开测试版的固定证书，关闭调试；清单兼容两个旧版查询标识，不改变证书校验。 |

覆盖安装保留用户数据目录中的配置、Key 和历史；不要为了更新卸载应用。Termux、Debian、虚拟机和 CLI 按各自的方式升级。

## 自动测试版

推送到 `main` 或手动运行 **Tri-platform build** 会构建、测试三端。CI 在独立 checkout 内按 `github.run_number` 增加各端数字版本，不改写源码中的版本。全部成功后先建草稿，上传三端安装包、`SHA256SUMS.txt`、`update.json`，最后公开 Release。Release 完整公开后才推进对应的 `update-feed/stable.json` 或 `preview.json`；稳定版另外推进兼容用的 `update.json`。发布脚本按通道保留另一通道文件，并拒绝低于当前通道现有版本或 Android build 的旧构建，避免并行工作流使更新清单倒退。

更新说明默认取 `docs/preview-notes.zh-CN.md`，可手动输入本批说明。版本从真实产物读取，清单由 `scripts/build-update-manifest.py` 生成，包含渠道、架构、版本、地址、大小、哈希；Android 额外记录版本代码和签名类型。

Android 测试包的签名必须固定。Actions secret `WORKBENCH_ANDROID_PREVIEW_KEYSTORE_BASE64` 存放既有开发签名密钥，CI 恢复后通过显式签名路径构建 debug APK，再比较 APK 证书与恢复的密钥证书，避免 runner 默认调试签名导致不能覆盖。密钥不可进入仓库、日志或发布附件。已有其他签名的安装只能使用同签名来源的包。

Windows 单独工作流也只发布可手动下载的测试版；三端应用内更新继续使用完整发布清单。

## 显式正式发布

只有获得维护者明确授权后，才手动运行 **Tri-platform build**，将 `channel` 设为 `stable` 并填写 `stable_version`（如 `1.0.0`）。必须从 `main` 分支运行，三端使用完全相同的版本号；Mac 构建号和 Android `versionCode` 仍按工作流序号递增。普通推送与未指定模式的运行继续发布测试版。

正式版会额外执行 Android release 单元测试、构建 release APK，并验证证书与现有固定证书相同、应用未开启调试。清单同时为旧 `development` 查询入口和新 `release` 查询入口提供同一个 APK；这只是旧客户端的迁移别名，不允许其他证书覆盖安装。

全部测试和构建通过后，使用 `workbench-v版本号` 标签创建草稿，上传三端安装包、哈希和清单，再公开为正式版并设为 Latest，最后更新固定清单。发布说明取 `docs/stable-notes.zh-CN.md`，也可在手动运行时指定。正式版不表示已经有 Apple 公证或 Windows 商业代码签名，具体限制必须在发布说明中写明。

更新按数字版本防止倒退；例如安装 `1.0.0` 后，后续 `0.x` 测试包不会覆盖它，也不会使固定更新清单倒退。下一次正式升级须使用更高的正式版本号。已有安装不需要卸载，不触碰配置、Key、历史和运行环境。

## 版本成熟度

各端基础版本从 `0.x.y` 进入 `1.0.0` 时，客户端就会按版本号标记正式版，不需要改变 GitHub Release 的 Pre-release 设置。以后 `1.x.y` 及更高版本保持正式版，回到 `0.x.y` 则显示测试版。Android 安装仍要求同包名、同签名且 `versionCode` 递增；版本成熟度不改变签名规则。

第一版尚不能发现固定清单的旧客户端，需要从发布页手动覆盖安装一次带此逻辑的新客户端，之后应用内检查会优先读取固定清单。
